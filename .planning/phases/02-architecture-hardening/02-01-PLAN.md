<objective>
Close the concrete, evidence-based architecture gaps found in an audit of this repo against an external review's 5 pillars (DI, lifecycle, plugin system, transport abstraction, package boundaries) — the P0 (cheap/safe) and P1 (moderate) tiers only. Explicitly NOT doing: a DI/IoC container, a NestJS-style `@Module` system, or a plugin system for gRPC (see "Explicitly out of scope" below) — those were P2, and the user chose P0+P1, not "chase the reviewer's full checklist."

Purpose: some of what the audit found is architecture-score theater (missing `exports` maps nobody has exploited yet), but one of them is a real, currently-shipping bug (AWS silently drops plugin middleware — see the AWS dead-code must_have above), and the Plugin triplication is exactly the kind of copy-paste drift that produces bugs like it again. Fixing these raises real code quality without pushing HeliosJS toward NestJS's architecture (and NestJS's DI/module layer is literally why it's the slowest framework in this repo's own benchmarks — see helios-docs/docs/benchmarks.md's "NestJS is the slowest" bullet).

Output: exports maps + lint boundary check (package isolation you can trust, not just observe); one shared Plugin dispatch in core (three fewer sources of truth, one bug fixed); a shared RequestFactory interface; real e2e coverage for aws/azure closing empty scaffolded test directories.
</objective>

## Findings this plan is built on (verified this session, don't re-derive)

- **DI**: none anywhere except a narrow `@InjectGrpcClient` (gRPC-only, positional, one thing). Not in scope for this plan (P2).
- **Lifecycle hooks**: real, invoked, adapter-local (http/aws/azure each independently define+call `onInit`/`onStart`(http only)/`onStop`(http only)/`beforeRequest`/`beforeRoute`/`afterResponse`). This plan's Plugin consolidation (Task 3) *is* the lifecycle-contract fix — there's no separate "lifecycle" work beyond it. gRPC has zero hook mechanism (`start()`/`stop()` are plain methods) — **not extended in this plan** (see "Explicitly out of scope").
- **Plugin system**: real, e2e-tested for http (`__tests__/http/e2e/http-plugins-pipeline.test.ts`), unit-only for aws/azure, absent for gRPC. Three independently-copied `usePlugin`/`callPluginHook`/`callPluginMethod` implementations (`src/{http,aws,azure}/src/utils/{http,aws,azure}/plugin.ts`) — **byte-for-byte identical dispatch logic**, diverging only in the adapter-specific `Hooks`/`Plugin` *types* they're parameterized over. One real bug found: AWS's copy carries a `middlewares: MiddlewareCB[]` field and `if (plugin.middleware) middlewares.unshift(...)` that **nothing ever reads** — `grep -n "middlewares" src/aws/src/lambda.ts` returns zero hits. Azure's copy correctly has neither the field nor the check (and its `Plugin` type correctly doesn't declare `middleware` either) — AWS is the outlier, not Azure.
- **Transport abstraction**: the shared piece is the *output* type (`Request`/`Req`), not the *process* — `RequestFactory.create` exists 3x (http/aws/azure) with no common interface, different arities, independent normalization logic. gRPC never produces a core `Request` at all (deals in raw proto messages — `RequestSource` type doesn't even list `'grpc'`) and isn't touched by this plan.
- **Package boundaries**: only `@heliosjs/core`'s package.json has an `exports` map; the other 5 have none. No lint rule anywhere restricts cross-package imports. In practice zero violations exist today (`grep -rn "from '@heliosjs` src __tests__ benchmarks` shows only bare-root imports, confirmed against vitest.config.ts's aliases, which also only alias bare package roots for the 5 non-core packages) — this is about locking in what's already true, not fixing an active violation.
- **Integration/architecture tests**: solid for http+core+middlewares (real e2e, real server, real fetch). `__tests__/{aws,azure,grpc}/e2e/` exist on disk but are **empty** — aws/azure have unit-only coverage (factories/normalizers/plugin), grpc has unit-only coverage of its own server/client. No architecture/import-boundary test exists anywhere.

## Explicitly out of scope (P2 — do not do reflexively)

- DI/IoC container, `@Injectable`/`@Inject`, provider scopes.
- A NestJS-style `@Module` system.
- A plugin/hook system for gRPC. Its request model (streaming, proto-typed, no single "raw request object" the way HTTP/Lambda/Azure Functions have) doesn't map onto the existing `Hooks` shape without real design work, and there's no evidence anyone needs it. If this changes, it's its own plan.
- Shared *runtime* normalization logic between http/aws/azure's RequestFactory (only a *type* contract is shared here — the header/cookie/query parsing itself stays adapter-specific, since Lambda/Azure event shapes are structurally different from `IncomingMessage`).
